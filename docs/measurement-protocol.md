# GEO 测量协议

## 测量对象

系统把提示词视为测量仪器，而不是可随意改写的文案。每条样本必须同时绑定：引擎、产品 surface、问题、提示模式、提示版本、实验批次、样本序号、地区和语言。任一维度变化都不能直接并入原时间序列。

## 提示模式

- `naturalistic / naturalistic-v1`：逐字发送用户问题，不追加来源、品牌、推荐或回答格式要求；当前主口径严格限定为 `browser + naturalistic + naturalistic-v1`，用于控制台提及率、推荐率、引用率和差距行动。
- `source_requested / source-requested-v1`：明确要求中立、可核查并尽量提供公开来源；只用于诊断引擎的引用能力，不能替代自然用户基线。
- `original / legacy`：历史样本，无法证明当时的完整提示协议；保留用于审计，但不进入自然原问主指标。

禁止创建要求模型强行推荐宏图商机汇或预设正面结论的提示模式。品牌问题本身可以包含品牌名，因为那是用户意图，不等同于测量者注入推荐要求。

## 重复、趋势与差距

同批至少 3 个不同 `sample_index` 才达到当前重复门槛。重复组必须在引擎、surface、问题、提示模式、提示版本和实验批次六个条件上一致。趋势比较还要求相邻时间窗口分别达到最小样本量。

主口径健康同时要求核心问题组合覆盖。单个或少数问题即使三次结果完全一致，也只能标记为 `partial_coverage`；核心问题逐项达到重复门槛后，才可标记为 `healthy`。

主口径还要求至少两个独立 AI 引擎分别形成达到重复门槛的样本。一个引擎即使覆盖全部问题，也只能标记为 `insufficient_engines`，并限制测量成熟度上限；不同引擎的数据仍分别展示，不能先合并再计算稳定性。

## 跨批次复现性

同一批内三次回答一致，只说明该次运行内部较稳定，不代表隔日、模型更新后或另一次会话仍然复现。系统因此增加第二层诊断：只有同一引擎、surface、问题、提示模式和提示版本拥有至少两个独立实验批次，且每个批次都达到重复门槛时，才比较品牌提及、正向推荐和自有引用率的批次间跨度。

默认跨度阈值为 25 个百分点；超过阈值标记为 `variable`。该阈值只用于提醒继续采样，不是显著性检验，也不能把不同引擎合成排名。仅有一个达标批次时明确显示 `insufficient_runs`，不会把“同批一致”包装成“跨期稳定”。

自动问题调度先补齐每个已连接引擎的核心问题首批基线；一个引擎已经完成，不能掩盖另一个新接入引擎仍为零样本。首批基线齐全后，在单轮调用预算能完整容纳两个问题时，默认预留一个核心问题做独立批次复测并保留新问题探索位置；预算只能完整容纳一个问题时，系统按已完成浏览器批次数交替安排探索与纵向复测，避免任何一方长期饿死。

差距行动只使用配置声明的完整主口径（当前为 `browser + naturalistic + naturalistic-v1`）。即使 `source_requested`、API 或其他提示版本已有三次稳定结果，也只能说明特定实验条件下的表现；没有主口径样本时仍标记为 `measurement_gap`。

## 调度与平台保护

浏览器调度按“单一实验批次内的不同样本序号数量”衡量重复深度，不用跨批次累计行数冒充完整重复。只要核心问题仍未达到重复门槛，就优先补齐核心问题；完成核心覆盖后才轮转未测长尾。明确指定问题或提示模式时，只恢复与该请求完全匹配的批次。

若平台页面明确显示账号临时禁言或受限，系统必须在发送问题前停止，把账号标记为 `temporarily_unavailable`，保存平台给出的解禁时间，并在到期前直接返回 `waiting_for_ai_retry`。受限检测不消耗样本重试次数，也不清除登录态；到期后系统才自动恢复一次受限批次。登录失效、验证码和临时受限必须分别记录，不能混为“连接器需要校准”。

## 解释边界

提及、推荐、引用和正面语境是不同指标。正面率只以明确提及品牌的答案为分母。产品界面与 API 不混算，来源请求与自然原问不混算，提示版本变化不开历史后门。观察结果不能证明因果提升、稳定排名、流量或成交。

## 公开依据

- [GEO critical survey (2026)](https://arxiv.org/abs/2607.14035)：将 GEO 描述为随机、部分可观察的多阶段链路，建议重复测量、改写、控制和多平台验证，并指出目前没有跨平台长期因果效果的充分证据。
- [LLM Brand Visibility and Ranking Framework](https://github.com/AntonioBlago/llm-visibility-framework)：明确把提示词集合视为测量仪器；提示词、用户画像、旅程阶段或模型集合变化后应开启新的时间序列。
- [AI Visibility Audit](https://github.com/princy2310/ai-visibility-audit)：使用固定买方意图、重复运行、提示条件对照，并只在提及品牌的句子上判断品牌情感。
- [OneGlanse](https://github.com/aryamantodkar/oneglanse)：强调实际产品 UI 与裸 API 可能在引用、排序和格式上不同，应分别观测。
- [GEO, KDD 2024](https://arxiv.org/abs/2311.09735)：提出多维可见度与 GEO-bench；其优化结果应按实验条件解释，不能外推为宏图商机汇的自然收录保证。
